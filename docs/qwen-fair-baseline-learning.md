# 学习单元 1：怎样证明前缀缓存真的有用

状态：AI 已辅助实现、复跑和写出证据；尚未收到用户答案，**没有任何本轮知识点被记为“本人确认掌握”**。这是待验证知识手册，不是个人能力认证。先完成本单元，再进入缓存异常与容量研究。

## 领域地图与学习顺序

推理优化解决的是：在质量与资源约束下，用更少成本完成相同任务。核心对象包括模型权重、输入 token、激活、每请求 KV 状态、计算后端、负载与计时边界。

先掌握：token/张量形状 → 自回归 prefill/decode → KV 中保存什么与位置 → 公平基线与计时 → 正确性和负结果。本单元只深入最后两个环节，并补齐前置形状。

进阶：量化误差与整数内核、请求调度与动态批处理、PagedAttention、性能 profiler、CUDA/昇腾。暂可忽略：多节点通信、自研 kernel 与大规模生产运维细节。MiniLM 是编码器，一次得到句向量；Qwen 在本实验里逐 token 生成，不能把前者批处理收益直接套到后者。

## 输入、输出与执行过程

输入是已分词整数列表 `tokens`，长度为 `P+S`，其中 P 是共享前缀长度，S 是问题等后缀长度。`prefix` 必须精确等于 `tokens[:P]`，且 S 至少为 1；完整前缀的最后 logits 未保存，所以本实现不接受空 suffix。

Qwen 配置：24 层，隐藏维度 896，14 个 Q 头、2 个 KV 头，每头维度 64。前缀输入 `[1,P]`，每层有效 K、V 各为 `[1,2,P,64]`；suffix 输入 `[1,S]`，状态增长到 P+S。模型返回 logits `[1,S,151936]`，取最后位置 `[:, -1, :]` 的 argmax 得到 `[1]` token，再 reshape 为 `[1,1]` 继续 decode。Q8 指权重，KV 此处仍是 FP16。

首次请求先计算前缀并保存独立状态，请求使用 clone；第二个请求命中则复制原前缀状态，不能拿第一个请求已追加过答案的 KV。新不复用基线则每次创建全新请求 cache，算完 prefix 直接续算 suffix，不创建共享快照。

`KVCache.state` 的 setter 按 K 的长度恢复 offset；直接路径靠正常 `update_and_fetch` 累加 offset。offset 决定位置相关计算，不能只复制数值却把位置当 0。本轮 probe 记录了每层 offset，而不是只凭“生成看上去合理”判断。

输出是生成 token 列表、TTFT、总耗时、decode 速度、缓存状态和可选阶段时间。强制生成 N=32 时 TTFT 到第 32 token 间有 N−1=31 个时间间隔：`decode_tps = (N−1) / decode_seconds`。最后输出的 token 不必再作为模型输入，因此最终 KV 不一定包含所有已经输出的 token。

逻辑 KV 字节 `M = 2 × L × Hkv × P × D × b`：2 是 K/V 两份，L=24 为层数，Hkv=2 为 KV 头数，P 为前缀长度，D=64 为头维度，b=2 为 FP16 字节数。它不包含请求副本、底层预分配和模型。

## 五个思维模型

|模型|是什么、为什么成立|适用问题|失效/遗漏条件|面试与工作怎么用|
|---|---|---|---|---|
|工作守恒与因果对照|比较相同输入、生成量、模型与采样；否则时间变化可能只是少做了任务|新旧基线是否公平|相同 API 不等于同计算图；缓存分配、同步、截断也会改变工作|指出旧基线额外 snapshot/clone，加入 direct，但不宣称全部差值都是 memcpy|
|Amdahl 与瓶颈迁移|总耗时由各阶段组成；只消去 prefill 不能消去 decode|为什么 TTFT 大降而总耗时改善有限|异步重叠时不能简单相加；诊断同步会改变原执行|先列 `T_total=T_prefix+T_suffix+T_decode+T_other`（本同步串行路径），用逐请求记录核对|
|摊销与复用经济性|构建成本要由后续命中分摊；多次重复才可能回本|首次 miss、短前缀、低命中率是否值得缓存|请求分布与淘汰、分配器、不同 suffix 会变化|用四请求含 miss 的总耗时回答，而不是只选最热 hit；任务 2 再研究容量阈值|
|状态所有权与不变量|可变状态有明确所有者，才能避免上一请求污染下一请求|KV 隔离、offset、淘汰与异常|单线程验证不证明并发安全；同值不代表无别名|问“谁能修改保存的 prefix”；用交错重放、offset 检查和注入故障验证|
|测量可观测性与外推边界|仪器、同步、负载和样本数都是测量条件|profile 是否改变结果、是否能声称 P99|同机短时重复不能代表线上和跨设备；hash 也不证明内容正确|分开不插桩主测量与诊断；保留原始记录、分母和负结果，现场可重算|

## 三个常见工程分歧

这些是需要按条件取舍的问题，不是声称整个学界存在统一阵营或结论。

1. **不复用基线该完整计算还是分段？** 完整路径接近“从头运行”的应用对照；分段路径便于隔离前缀重算/复用。在本轮完整与分段本身就有耗时差异，这是两种对照都要保留的证据。隐含假设分别是代表应用路径、或控制分段结构。共识是标明分母并保持任务相同；没有一个分母能回答所有问题。实践中同时报告 full 与 direct，旧 snapshot 路径只作为历史归因对照。

2. **共享状态应深拷贝还是零拷贝/写时复制？** 独立快照易于推理所有权；共享/写时复制可能节省物理开销，但依赖后端别名和写入语义。本轮独立请求 token 一致与污染检查支持功能隔离；并未测出真正物理拷贝带宽，也未实现底层 copy-on-write。共识是不能允许跨请求污染，具体复制策略没有跨后端通用最优解。当前先保留可验证隔离；没有复用的 direct 路径无需复制，不能类推命中路径也可随意共享可变对象。

3. **为准确归因加同步，还是尽量不打扰性能？** 同步阶段计时更易解释惰性 GPU 计算；减少同步更接近实际执行，但主机时间可能只测提交。本轮 profile 与无 profile 耗时不同，支持“诊断有观察成本”，不能证明差异全由同步造成（温度、时段也变化）。共识是完成 GPU 工作后再解释计时；无法凭这一小实验判定所有 profiler 的最佳方式。实践中双轨测量，不从插桩中位数推导无插桩端到端速度。

## 30 秒面试回答

“我在 AI 辅助的 Qwen 前缀缓存项目里发现，旧不复用基线仍建立快照再复制，请求本身并不需要。于是保留旧基线，增加直接续用本请求 KV 的分段对照，并把主计时和同步诊断分开。M4 Max 上，2048-token 前缀、四个各生成 32 token 的请求，计入首次 miss 后从 1.003 秒降到 0.630 秒，下降约 37.2%。去掉快照没有稳定加速基线，主要收益来自免去重复前缀计算，decode 基本不变。代码和数据已验证，我本人正在完成独立复跑和解释。”

掌握后可根据实际个人贡献调整最后一句；不要提前删掉 AI 辅助归属。

深入追问：为什么完整 prefill 和分段本身不同？`mx.eval` 与 `synchronize` 在本计时里各负责什么？保存的 KV 是否含最后生成 token？哈希绑定哪些文件？为什么 profile 的阶段中位数之和不等于总耗时中位数？请先画路径，再指代码和原始记录。

常见错误回答：“TTFT 降 94% 所以生成快 94%”；“Q8 所以 KV 也是 INT8”；“有 hash 就自动检测模型运行期变化”；“800 请求证明 P99”；“token 一致所以答案正确”；“复制 API 花 0.1ms，已经证明了显存带宽”。这些结论分别混淆时间分母、量化对象、身份约定、统计独立性、正确性层级和物理行为。

## 工程检查清单

- 固定模型/配置/分词器指纹、完整 token 与输出长度。
- 先保存假设与验收，再运行，失败也保留。
- no reuse 不触碰 store，hit 不重新 prefill prefix，miss 构建计入工作流。
- offset、隔离与逐 token 对照正确；输出目录不覆盖历史。
- 逐请求阶段可对账，工作流额外开销另有总 wall time。
- 只用主测量报告端到端结果；诊断只解释来源。
- 区分历史实测、本轮实测、离线证据验证、计划、本人掌握。
