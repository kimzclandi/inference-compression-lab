# 学习单元 2：缓存失败为什么不能算“完成了一半”

本轮代码和实验由 AI 辅助完成；用户尚未作答或亲自复跑，本单元所有能力仍为待验证。继续沿用单元 1 的领域地图：模型计算 → 请求 KV → 共享快照 → 查找/容量/失效 → 测量。本单元必须掌握状态所有权、提交边界、LRU 和字节预算；并发锁、分布式事务、分页 KV 暂不展开。

## 当前主干

输入：模型身份字符串、精确 token 元组、builder（返回快照和逻辑字节数）、clone（返回请求私有 KV）。输出：私有 KV 与 hit/miss/bypass 状态，或异常。MLX 模型中每层 K/V 有效形状各为 `[1,2,P,64]`，24 层；P 是前缀 token 数。字节数 `2×24×2×P×64×2`，第一个 2 是 K/V，最后一个 2 是 FP16 字节数。

问题：旧路径先淘汰 A、放入 C，再复制 C。复制失败时，请求没有成功，A 却已经没了。命中失败还会提前把旧条目提升到 LRU 尾部。

新执行顺序：校验/查找 → 构建（仅 miss）→ clone → 在临时元数据表上计算淘汰和占用 → 提交条目及成功计数。hit 也只有 clone 成功后才更新 LRU 和命中数。builder/clone 抛异常时，原有条目、顺序、逻辑字节和成功计数保持原样，failures 加一。

“临时元数据表”只复制键与引用，不复制所有 KV 张量。它的代价随条目数增长，当前缓存只有 2/3 条目；不能推断适合百万条目。clone 必须不修改输入，builder 必须交出独立快照；单调用者、无回调重入是前提。此实现不是任意恶意回调、真实 OOM 或并发写入的全面事务系统。

## 五个思维模型在本单元的落点

|模型|为什么有用|什么时候会失效|面试/工程用法|
|---|---|---|---|
|事务提交边界|把可能失败的准备与可见状态更新分开，才能定义失败后不变量|回调主动改原快照、重入、并发、无法恢复的进程崩溃|圈出 commit 之前的 builder/clone，解释故障注入点|
|所有权与别名|请求续写不能改共享前缀，否则影响后续请求|clone 返回别名或原地修改源|看 tensor shape/offset，加交错请求重放；不只比较 cache 长度|
|工作集与容量阈值|循环 A/B/C 的复用距离超过两条目容量，每次访问都 miss|非 LRU、不同访问序列、不同大小、预算先成为瓶颈|手推访问表，再测两/三条目；不要先看结果倒写预测|
|多维资源约束|条目上限和字节上限都必须满足，有三位置不等于放得下三份数据|把逻辑字节误当 RSS，忽略请求副本和临时构建|同时报告 max_entries 与 max_bytes；观察有效容量由较紧约束决定|
|可审计计数|成功、失败、绕过要有清晰定义，指标才可解释|混用尝试次数和成功次数、clear 暗中重置分母|成功 miss 包含 bypass；failures 独立；clear 仅清驻留内容，累计计数保留|

## 三个工程取舍

1. **失败是否允许改变 LRU？** 可以将访问意图算热度，也可以只按成功获得缓存更新。本项目选择后者，目的是可预测地保存原请求工作集；代价是失败请求不增加热度。没有跨业务通用最优语义，必须明确计数与淘汰规则。本轮旧失败记录和新故障注入是本选择的验证证据。
2. **先释放旧条目还是先生成请求副本？** 先释放可降低部分峰值压力，却可能在构建失败时丢失仍可用数据；先复制便于失败回滚，但会暂时同时持有旧快照、新快照和副本。本项目选后者，只承诺驻留逻辑字节预算，不承诺进程内存硬上限。真实内存压力下的选择仍需单独测量。
3. **提升容量是否就是优化？** 大容量在工作集刚好跨阈值时可能显著增加命中，代价是驻留内存增加；小容量节省内存却可能反复淘汰。证据应同时看命中、耗时和占用，不以“缓存越大越快”为定理。本轮三条目但预算仅容两条的对照验证双重约束，不能外推到真实流量分布。

## 30 秒回答

“我在 AI 辅助审计前缀缓存时复现了一个错误路径：新请求 clone 失败，旧实现仍淘汰有效条目并计入成功。修复把 builder 和 clone 放到提交前，失败只更新失败计数，并用真实模型故障注入验证原条目重放输出不变。还预先预测并测试了三前缀循环访问：两条目反复淘汰，三条目且字节充足才有复用。这里的预算是逻辑 KV 字节，不是进程内存上限。”

深入追问：为什么 hit 也可能失败？为什么先 clone 后淘汰增加临时内存？clear 后 hit/miss 是否归零？换权重但不换身份会怎样？如果 clone 修改原快照后再抛异常，你的保证还成立吗？

常见错误：“异常捕获了就安全”；“三个条目必有九次命中”；“预算 24MiB 所以程序只用 24MiB”；“只要加 try/except 就是线程安全”；“注入异常等于测试了真实显存不足”。

工程检查：先记录 resident tokens/LRU/stats；分别注入 hit/miss/bypass clone、builder、非法 size；检查成功计数不变且 failures 增一；真实重放 token；检查清空后 miss；同时验证条目与字节限制；保留失败版本输出。
