# 校招项目模拟审查：MiniLM 量化与 CPU 推理优化

审查性质：模拟工程面试官对项目材料的评估，不是招聘方意见或用户已通过面试的证明。目标是“可作为中等偏上工程型校招生的一个项目素材”；不以文档长度、测试数量或框架名称数量评分。最终数值与工程验收见 runtime study 报告。

## 初审与本轮迭代

| 审查问题 | 原先不足 | 本轮补充 |
|---|---|---|
| 是否只会 export/quantize 调用？ | 有粒度对照和误差分析，但实际运行配置未优化 | 实现可配置 runtime，固定协议比较线程数，锁定后复验 |
| 优化收益能否归因？ | 只有不同精度之间的对比 | 同一 INT8 模型4线程/调优线程对照，另给独立调优 FP32 |
| 是否重复使用同一批输入获得最好数字？ | 单一固定计时输入 | 16请求循环，开发/确认行范围分离，8轮确认；多形状交叉检查 |
| 质量是否只停留在已探索的 validation？ | 选层和全量结果都来自 validation | 冻结配置后首次使用官方 STS-B test split；不称全新盲测 |
| 有无能运行的交付物？ | 实验脚本为主 | 带哈希验证的部署配置和实际句向量 CLI |
| 能否解释不符合预期的结果？ | 容易只写文件压缩和正向数字 | 保留未优化诊断偏差、量化变慢、形状与资源消耗边界 |

## 审查标准

1. 真实模型、模型/数据版本与结果能对应，历史结果不被覆盖。
2. 量化范围与实际执行精度可核验，不用文件大小替代运行内存。
3. 提出具体假设，改变受控变量，使用独立的后续输入确认。
4. 有质量约束下的性能或成本权衡；负结果照实保留。
5. 代码可以执行并对错误输入/模型版本给出合理拒绝，结果可追溯。
6. 能解释局部/累计误差、测试集边界、量化/API/个人贡献，不依靠夸大表述。

前五项主要可审查项目材料；第六项中的个人理解必须通过用户答题、复跑和现场修改验证，不能由 Codex 的运行结果代替。

## 仍然可能被面试官追问的不足

- Thread tuning 是运行时配置优化，技术门槛低于实现高性能 kernel；不要单独把调线程写成算法创新。
- MiniLM 是编码器，本项目没有真实生成式大模型的 prefill/decode、KV cache、连续批处理或多卡通信实验。
- profiler 是算子级观察，尚未通过系统级时间线或硬件计数器完全解释所有 INT8 相对 FP32 的开销差异。
- 日常使用的单台 M4 Max，没有固定温度、功率、CPU核心亲和性；结果不代表其他机器或长期生产负载。
- 没有 Jetson 真机的本轮量化测试，不能将 Mac CPU 成果改名为 Jetson/TensorRT 实测。

因此，材料可以达到“有完整工程闭环的校招项目”标准，但不能据此断言对所有 AI Infra / 大模型推理岗位 overqualified。针对底层算子/编译优化岗位，它更适合作为补充项目；针对偏模型部署与推理评测的岗位，匹配更直接。

## 个人面试就绪检查（待用户完成）

- 不看报告，从原始JSON重新算出线程优化的时延比例，并解释为什么这不等于量化本身带来的加速。
- 解释量化图中哪些算子仍是浮点，以及 profiler 提供和不提供什么证据。
- 修改一个测试形状或线程候选，使用新目录复跑，解释收益为何可能变化。
- 解释 test split 的使用时机、预训练重叠未知，以及 why no post-test retuning。
- 准确区分本人历史负责、当前 AI 辅助实现、ORT 官方能力和未完成项。

这些检查通过之前，简历可用作项目事实描述，但不应宣称已经独立掌握全部实现。
